# Функции

Минимум, чтобы продукт стал полезен. Что никогда не делаем — раздел «Вне скоупа» внизу.

## Загрузки
- Добавление по URL (модалка по `a`, префилл из буфера обмена, если там URL).
- HTTP(S).
- **Пауза / возобновление** через Range-запросы; ресюм после перезапуска процесса.
- **Параллельная загрузка (воркеры)**: N соединений на файл, если сервер поддерживает Range; иначе fallback на одно соединение.
- **Streaming-режим** при неизвестном `Content-Length`: один воркер, append в `.data.brook`, прогрессбар indeterminate, без resume. Нужно, чтобы поддерживать ссылки вида GitHub codeload и прочие CDN, которые не сообщают размер заранее.
- **Редиректы 3xx** разворачиваются один раз на `inspect`; эффективный URL сохраняется в `file_settings` — range-GET'ы идут сразу на конечный CDN-ресурс без лишних 3xx-хопов и повторного резолва подписанных ссылок.
- **Потоковая запись на диск** — буфер 64–256 KB на воркер, прямой `pwrite` в пре-аллоцированный файл по offset'у. RAM-бюджет процесса постоянен и не растёт от размера файла.
- **Пре-аллокация + общий индекс**: `<filename>.data.brook` пре-аллоцируется полным размером (`F_PREALLOCATE` на macOS). Статус каждого piece'а лежит в общей SQLite-базе `./brook.db` (таблица `pieces`, WAL). Батчевый `fsync` + коммит каждые 16 кусков. По завершении — `rename` в `<filename>`, piece-строки загрузки удаляются. Несовпадение inspect-полей или числа piece-строк ⇒ рестарт загрузки с нуля. Детали — [architecture.md#раскладка-на-диске](architecture.md#раскладка-на-диске).
- Дефолты и потолки (число воркеров на файл, число одновременных активных задач, дефолтная папка `~/Downloads`) читаются из таблицы `settings` в `brook.db` на старте демона.
- Прогресс: процент, скорость, ETA, «скачано / всего».
- **Cancel** — остановка + удаление `.data.brook` и piece-строк загрузки в `brook.db`; запись остаётся в списке со статусом `CANCELLED`. **Remove** — дополнительно убирает запись из очереди. Обе команды — с подтверждением в UI. Полная семантика — [api.md#семантика-команд](api.md#семантика-команд).
- Ретраи с экспоненциальным бэкофом и лимитом попыток.

## API (gRPC)
- **Единственный путь** между UI и движком — gRPC. Схема в `brook-proto`. См. [api.md](api.md).
- Сервер (`brookd`) слушает только `127.0.0.1` (loopback).
- Контракт: unary команды (`Add`, `Pause`, `Resume`, `Cancel`, `List`, bulk `PauseAll`/`ResumeAll`) + server-streaming событий (progress, state changes).
- Settings через API в MVP не входят — см. раздел «Конфигурация» ниже.

## Процессы
- **`brookd`** — демон, содержит `brook-core` и `brook-api`. Берёт single-instance lock в CWD, открывает `brook.db`, слушает gRPC. Без UI.
- **`brook`** (крейт `brook-tui`) — ratatui-клиент. gRPC к `brookd` на `127.0.0.1:<port>` (флаг `--port`, дефолт 7090). Клиентов можно запускать сколько угодно — все видят одно состояние через `Watch`.

## Конфигурация (БД)
- TOML-файлов нет. Вся конфигурация — в таблице `settings` внутри `./brook.db`.
- `brookd` на первом старте создаёт БД и сидит `settings` дефолтами.
- Параметры: дефолты загрузок (воркеры, параллельность, папка), порт API, пути логов, поведение при дубликатах. Ключи — [architecture.md#конфигурация](architecture.md#конфигурация).
- Правка в MVP — через SQL при остановленном демоне. API-методов и hot-reload нет.
- Невалидное значение → ошибка старта `brookd` с явным сообщением.

## UI — `brook` (ratatui)
- Клавиатурное управление в терминале.
- Шорткаты: `a` add, `p` pause, `r` resume, `c` cancel, `o` open, `/` filter, `q` quit, `?` help.
- Навигация: `↑` / `↓` и `j` / `k`.
- **Разворот деталей** по `Enter` — под строкой расширенная карточка (полный URL, путь, воркеры, последние события).
- **Multi-select** клавиатурой: `Space` — toggle, `Shift` + стрелки — диапазон. Команды `p`/`r`/`c` применяются ко всем выделенным.
- Фильтр списка по `/` — по имени файла / URL.

## Обработка дубликатов — `ask`
- URL уже в очереди → модалка: `Open existing` / `Add anyway` / `Cancel`.
- Файл уже есть на диске → клиент автоматически подбирает `<stem> (N).<ext>` и молча ретраит `Add`; в списке появляется новая запись, toast подсказывает финальное имя.

## Наблюдаемость
- **Структурированные логи JSON** через `tracing`.
- CorrelationId: `session_id` (на запуск процесса), `download_id` (на каждую загрузку). Оба поля — в каждом событии.
- Файл `~/Library/Logs/brook/brook-<session_id>.jsonl` + stderr.

## Вне скоупа
- Торрент / magnet — отдельный большой движок.
- Мобильный клиент.
- Облачная синхронизация очереди между устройствами.
