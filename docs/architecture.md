# Архитектура

## Принципы
- Движок загрузок (`brook-core`) не знает про UI и API — чистая библиотека.
- UI и удалённые клиенты общаются с движком **только через gRPC**.
- Каждая активная загрузка — отдельный актор (tokio-task). Над ними — единый оркестратор.
- RAM-бюджет на одну загрузку — константный; запись на диск идёт чанками.

## Структура workspace

```
brook/                            # workspace root
├── Cargo.toml                    # [workspace]
├── proto/
│   └── brook/v1/brook.proto      # единый источник правды контракта API
├── crates/
│   ├── brook-proto/              # build.rs → prost + tonic stubs
│   ├── brook-core/               # Orchestrator + DownloadEngine
│   ├── brook-api/                # gRPC-сервер (tonic), обёртка над core
│   └── brook/                    # MVP-бинарь: ratatui-UI, стартует core+api локально
└── docs/
```

Клиенты после MVP (`brook-app`, `brookd`) — см. [post-mvp.md](post-mvp.md).

## Процессная модель
`brook` при старте поднимает внутри себя:
1. Читает TOML-конфиг из CWD (`./brook.toml`).
2. `Orchestrator` (`brook-core`) — асинхронная задача.
3. gRPC-сервер (`brook-api`) на `127.0.0.1:<port из конфига>` — асинхронная задача.
4. Рендерит ratatui-UI, который является gRPC-клиентом к локальному серверу.

**UI никогда не дёргает `Orchestrator` напрямую** — только через API. Даже внутри одного процесса. Это даёт равенство: завтра любой другой клиент (локальный или удалённый) работает по тому же контракту.

## Модель акторов в `brook-core`

### `DownloadEngine` (один на загрузку)
Владеет всем для жизненного цикла одной загрузки:
- Сегменты (N tokio-задач), их прогресс и состояние.
- Диск-writer: **запись чанками фиксированного размера** (ориентир 64–256 KB), без буферизации всего файла. RAM на одну загрузку — константный, не зависит от её размера. Раскладка файлов — [см. ниже](#раскладка-на-диске).
- Retry-логика с экспоненциальным бэкофом.
- История смен состояний.

- Вход: mpsc-канал команд (`Pause`, `Resume`, `Cancel`).
- Выход: broadcast-канал событий (`Progress`, `StateChanged`, `SegmentUpdate`, `Completed`, `Failed`).

### `Orchestrator` (один на процесс)
- Реестр `DownloadEngine`-ов (по `DownloadId`).
- Очередь: сколько задач активно, кто ждёт.
- Принимает команды из `brook-api` и роутит в нужный engine.
- Агрегирует события всех engines в один broadcast-поток для API.
- Отвечает за персистентность очереди (SQLite) и применение конфига.

### Почему именно так
Пользователь: «Один `DownloadEngine` на загрузку и один оркестратор на процесс». Это стандартная актор-модель: каждый engine изолирован, тестируется отдельно, падает независимо. Оркестратор — единственная точка координации.

## Раскладка на диске

На каждую активную загрузку — три артефакта рядом в целевой папке.

### Артефакты

1. **`<filename>.data.brook`** — пре-аллоцированный файл **полного финального размера**, заполненный нулями. Создаётся один раз перед стартом загрузки (sparse / `F_PREALLOCATE` / эквивалент). Готовые чанки записываются в свои offset'ы поверх нулей.
2. **`<filename>.chunk.<N>.brook`** — временные файлы чанков. Сегмент сначала скачивает тело Range-запроса в такой файл; только после полной загрузки чанк переезжает в `.data.brook`.
3. **`<filename>.index.brook`** — SQLite-база рядом с `.data.brook`. Хранит: URL, общий размер, размер чанка, число чанков, статус каждого чанка (`pending` / `in_progress` / `done`), кастомные заголовки, отметки времени.

### Именование N

Ширина поля `N` — число десятичных разрядов общего количества чанков (нулевое паддинг-заполнение):

| Чанков     | Ширина | Примеры                    |
|------------|--------|----------------------------|
| 1–9        | 1      | `3`, `7`                   |
| 10–99      | 2      | `04`, `12`, `99`           |
| 100–999    | 3      | `007`, `123`, `999`        |
| 1000–9999  | 4      | `0001`, `0123`, `1235`     |
| 10000+     | 5+     | `00001`, `45678`           |

Это даёт лексикографически отсортированный `ls` и визуальную стабильность имён.

### Жизненный цикл чанка

1. Сегмент открывает Range-запрос на диапазон чанка `N`, тело пишется в `<filename>.chunk.<N>.brook`.
2. По полной загрузке чанка — атомарная запись по нужному offset'у в `<filename>.data.brook`, затем `fsync`.
3. `<filename>.chunk.<N>.brook` удаляется.
4. Статус чанка в `<filename>.index.brook` обновляется на `done`.

Инвариант: статус `done` в индексе означает, что чанк гарантированно лежит в `.data.brook`. Порядок операций 2 → 3 → 4 обеспечивает это.

### Завершение

Когда все чанки `done`:
1. `<filename>.data.brook` → `<filename>` (`rename`).
2. `<filename>.index.brook` удаляется.

### Ресюм и сбои

- **Чистый перезапуск процесса**: читаем `.index.brook`, пропускаем чанки `done`, чанки в `in_progress` (и все `pending`) перезакачиваем с нуля. Остаточные `.chunk.N.brook` от незавершённых чанков удаляются перед перезагрузкой.
- **`kill -9` посреди записи чанка**: инвариант выше означает, что чанк либо `done` в индексе и лежит в `.data.brook`, либо его статус не `done` — и тогда мы его перезакачиваем. Полузаписанных «зомби»-чанков в `.data.brook` не бывает.
- **`.index.brook` повреждён или удалён**: доверять `.data.brook` нечем. Удаляем `.data.brook`, все `.chunk.*.brook` и пересоздаём индекс. Загрузка стартует с нуля.
- **`.data.brook` удалён, индекс цел**: симметрично — удаляем индекс и чанки, стартуем с нуля.

### Чанк vs сегмент

- **Чанк** — единица записи в файл и единица прогресса в индексе. Размер фиксирован (64–256 KB).
- **Сегмент** — параллельная HTTP-Range-задача. Один сегмент последовательно качает назначенные ему чанки.
- Для файла в 1 GB при чанке 256 KB и 4 сегментах: 4096 чанков, 4 сегмента по ~1024 чанка на каждого.

## API-слой (`brook-api`)
- Генерируется из `.proto` через `tonic-build` в build.rs `brook-proto`.
- Тонкая обёртка вокруг `Orchestrator`: proto ↔ core.
- Запускается как фоновая задача бинаря `brook`.
- Контракт — [api.md](api.md).

## UI-слой (`brook`)
- `ratatui` + `crossterm`.
- gRPC-клиент (`tonic::Channel`) на локальный сервер.
- Две точки взаимодействия:
  - Команды — unary (`add`, `pause`, ...).
  - События — подписка на server-streaming (`Watch`); фоновая задача питает view-model.
- View-model мутируется **только** в ответ на событие от API.
- UX-детали — [ux.md](ux.md).

## Конфигурация

В MVP — `./brook.toml` в текущей рабочей директории. `brook` читает «из-под ног»: смотрит в CWD при старте. Если файла нет — создаёт с дефолтами, путь пишется в stderr. Неизвестные ключи → warning в лог; недопустимые значения → ошибка старта с явным сообщением.

После загрузки передаётся в `Orchestrator`. Изменения на лету не поддерживаются (hot-reload и API-методы на settings — см. [post-mvp.md](post-mvp.md)).

Черновик структуры:

```toml
[download]
default_segments = 4
max_segments = 16
max_concurrent = 3
default_dir = "~/Downloads"
on_duplicate_url = "ask"       # ask | skip | add
on_file_exists = "ask"         # ask | rename | overwrite

[api]
port = 7090
bind = "127.0.0.1"

[log]
dir = "~/Library/Logs/brook"
rotate_count = 10
rotate_size_mb = 50
```

## Наблюдаемость

- `tracing` + JSON-форматтер во всех крейтах.
- `session_id` — UUID, создаётся при старте процесса; прокидывается как поле во всех root-спанах.
- `download_id` — у каждой загрузки; `brook-core` входит в `span!(download_id = ...)` при любых операциях.
- gRPC-запросы получают `request_id`; если касаются конкретной загрузки — добавляется `download_id`.
- Лог-файлы: `~/Library/Logs/brook/brook-<session_id>.jsonl`. Ротация — [open question](open-questions.md).

## Тестирование
- `brook-core` — юнит + интеграционные без сети (`wiremock` или локальный тест-сервер). Отдельный тест: **пиковый RSS при длительной загрузке не растёт с размером файла** (проверка чанковой записи).
- `brook-api` — интеграционные: tonic-server + tonic-client в одном процессе, проверка контракта.
- `brook` — ручная прогонка квалификационных сценариев (см. [open-questions.md](open-questions.md)).
