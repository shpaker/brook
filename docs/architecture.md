# Архитектура

## Принципы
- Движок загрузок (`brook-core`) не знает про UI и API — чистая библиотека.
- UI и удалённые клиенты общаются с движком **только через gRPC**.
- Каждая активная загрузка — отдельный актор (tokio-task). Над ними — единый менеджер.
- RAM-бюджет на одну загрузку — константный; запись на диск идёт кусками.

## Структура workspace

```
brook/                            # workspace root
├── Cargo.toml                    # [workspace]
├── proto/
│   └── brook/v1/brook.proto      # единый источник правды контракта API
├── crates/
│   ├── brook-proto/              # build.rs → prost + tonic stubs
│   ├── brook-core/               # гексагональное ядро: domain + ports (+ services); без сети и диска
│   ├── brook-http/               # HTTP-адаптер: reqwest + middleware, реализует HTTP-порты ядра
│   ├── brook-api/                # gRPC-сервер (tonic), обёртка над core
│   ├── brookd/                   # MVP-бинарь: демон, поднимает core + api + адаптеры
│   └── brook-tui/                # MVP-бинарь: ratatui gRPC-клиент (имя бинаря — `brook`)
└── docs/
```

Клиенты после MVP (`brook-app`) — см. [post-mvp.md](post-mvp.md).

## Процессная модель

В MVP — **два процесса**: демон `brookd` и TUI-клиент `brook` общаются только по gRPC. Это не оптимизация на будущее, а условие целостности контракта: UI равноправен с любым другим клиентом (в том числе удалённым, в post-MVP).

### `brookd` (демон)
1. Берёт single-instance lock на `.brook.lock` в CWD (флок).
2. Открывает `./brook.db` (SQLite); при первом старте — сидит таблицу `settings` дефолтами.
3. Читает `settings` из БД, применяет при инициализации.
4. Поднимает `DownloadManager` (`brook-core`) — асинхронная задача.
5. Запускает gRPC-сервер (`brook-api`) на `127.0.0.1:<port из settings>` — асинхронная задача.
6. Работает до `SIGTERM` / `SIGINT`.

### `brook` (TUI, крейт `brook-tui`)
1. `tonic::Channel` на `127.0.0.1:<port>` (порт задаётся флагом `--port`, дефолт `7090`).
2. Рендерит ratatui-UI, который является gRPC-клиентом к `brookd`.
3. Если демон недоступен — сообщение в UI и подсказка запустить `brookd`; автостарт демона в MVP не делаем.

**UI никогда не дёргает `DownloadManager` напрямую** — только через API. Завтра любой другой клиент (локальный или удалённый) работает по тому же контракту.

## Архитектурный стиль `brook-core`

Ядро следует паттерну **Hexagonal Architecture** (он же Ports & Adapters). Граница «чистое/грязное» совпадает с границей крейта: всё, что внутри `brook-core`, не знает про сеть, диск и ОС; всё, что снаружи, — знает.

- **Domain** — сущности и value-объекты: идентификатор загрузки, спецификация задачи (url, target_dir, воркеры), конечный автомат состояний, снимок прогресса, агрегат `Download` (spec + runtime-поля), события от engine к подписчикам и команды от клиента к engine. Это чистые типы без I/O и без зависимостей на внешний мир.
- **Ports** — трейты, через которые ядро обращается наружу: [`TPieceStorage`](#абстракция-хранилища-tpiecestorage) и `TPieceStorageFactory` для хранения кусков, [`TQueueStore`](#абстракция-очереди-queuestore) для персистентности очереди, `THttpInspect` и `TRangeFetch` для сетевого ввода-вывода. Это *outbound*-порты: ядро — клиент (вызывает методы), адаптер — сервер (реализует).
- **Services** (появятся на этапе 1.3+) — application-координаторы [`DownloadManager`](#downloadmanager-один-на-процесс) и [`DownloadEngine`](#downloadengine-один-на-загрузку). Используют domain и ports, сами I/O не трогают.
- **Adapters** живут **вне** `brook-core`: SQLite-реализации (`SqliteTQueueStore`, `LocalPieceStorage`) — в `brookd`; HTTP-адаптер (`HttpInspectClient`, `RangeFetchClient`) — в отдельном крейте `brook-http`, `brookd` подключает его как зависимость; gRPC-адаптер — в `brook-api`. Тестовые in-memory адаптеры (`MemoryTQueueStore`, `MemoryPieceStorage`) — в test utils самого `brook-core`, но отдельным модулем, не подмешанным в продовый код.

Что это даёт: ядро тестируется без сети и без диска (порты подменяются in-memory или `wiremock`-адаптерами); смена бэкенда хранилища или HTTP-клиента не требует изменений в ядре; статическая гарантия — если файл лежит в `brook-core`, у него нет зависимости на `rusqlite` или `reqwest` (проверяется через `cargo tree -p brook-core`).

## Модель акторов в `brook-core`

### `DownloadEngine` (один на загрузку)
Владеет всем для жизненного цикла одной загрузки:
- Воркеры (N tokio-задач), их прогресс и состояние.
- **`TPieceStorage`** — абстракция записи и индексирования кусков (см. [ниже](#абстракция-хранилища-tpiecestorage)). RAM-бюджет задаётся буфером 64–256 KB; кусок — 1–4 MB. `DownloadEngine` параметризован типом `S: TPieceStorage` и не знает про диск или S3.
- Retry-логика с экспоненциальным бэкофом.
- История смен состояний.

- Вход: mpsc-канал команд (`Pause`, `Resume`, `Cancel`).
- Выход: broadcast-канал событий (`Progress`, `StateChanged`, `WorkerUpdate`, `Completed`, `Failed`).

### `DownloadManager` (один на процесс)
- Реестр `DownloadEngine`-ов (по `DownloadId`).
- Очередь: сколько задач активно, кто ждёт.
- Принимает команды из `brook-api` и роутит в нужный engine.
- Агрегирует события всех engines в один broadcast-поток для API.
- Получает `TPieceStorageFactory` при инициализации — создаёт экземпляр `TPieceStorage` для каждой новой загрузки.
- Получает `TQueueStore` при инициализации — не знает, где и как хранится очередь (см. [ниже](#абстракция-очереди-queuestore)).

`brook-core` — **чистая библиотека**: нет зависимостей на БД, файловую систему или ОС. Всё I/O-специфичное скрыто за трейтами и живёт снаружи (в `brookd`).

### Почему именно так
Один `DownloadEngine` на загрузку, один менеджер на процесс — стандартная актор-модель: каждый engine изолирован, тестируется отдельно, падает независимо. Менеджер — единственная точка координации. `TPieceStorage` и `TQueueStore` как трейты позволяют переиспользовать `brook-core` без привязки к диску, SQLite или конкретной ОС.

## Абстракция хранилища (`TPieceStorage`)

`DownloadEngine` работает с кусками через трейт `TPieceStorage`, не зная деталей реализации. Трейт описывает пять операций: запись порции байт куска (`write_piece_bytes`), атомарный коммит батча завершённых кусков (`commit_batch`), получение списка незавершённых кусков для возобновления (`pending_pieces`), финализацию загрузки (`finalize`), прерывание с удалением артефактов (`abort`). Инвариант `commit_batch`: после возврата `Ok` байты гарантированно сохранены.

`DownloadManager` принимает фабрику `TPieceStorageFactory`, которая создаёт экземпляр `TPieceStorage` для каждой новой загрузки.

### Реализации `TPieceStorage`

| Реализация | Где живёт | Назначение |
|---|---|---|
| `LocalPieceStorage` | `brookd` | Основная: `pwrite` в `.data.brook` + `.index.brook` (SQLite WAL) |
| `MemoryPieceStorage` | `brook-core` (test utils) | In-memory, для юнит-тестов без диска |
| `S3PieceStorage` | внешний крейт | S3 multipart upload; локальный SQLite хранит ETag и part number |

Детали локальной реализации (`LocalPieceStorage`) — в разделе [Раскладка на диске](#раскладка-на-диске) ниже.

## Абстракция очереди (`TQueueStore`)

`DownloadManager` хранит очередь через трейт `TQueueStore` — без знания о SQLite или любой другой БД. Трейт описывает четыре операции: загрузку всех записей при старте (`load_all`), добавление новой загрузки (`insert`), обновление состояния (`update_state`), удаление записи (`remove`).

### Реализации `TQueueStore`

| Реализация | Где живёт | Назначение |
|---|---|---|
| `SqliteTQueueStore` | `brookd` | Основная: таблица `downloads` в `./brook.db` |
| `MemoryTQueueStore` | `brook-core` (test utils) | In-memory, для юнит-тестов без диска |

## Раскладка на диске

> Этот раздел описывает детали `LocalPieceStorage` — реализации `TPieceStorage` по умолчанию в `brook-core`. Другие реализации (S3 и т. д.) используют тот же трейт, но хранят данные иначе.

На каждую активную загрузку — **два артефакта** рядом в целевой папке.

### Артефакты

1. **`<filename>.data.brook`** — пре-аллоцированный файл полного финального размера. На macOS — `F_PREALLOCATE` (реальная резервация физических блоков) + `ftruncate` до целевого размера, без явного обнуления. Куски пишутся прямо сюда через `pwrite` по своим offset'ам.
2. **`<filename>.index.brook`** — SQLite-база рядом (WAL-режим, `synchronous=NORMAL`). Хранит: URL, общий размер, размер куска, число кусков, статус каждого куска (`pending` / `done`), кастомные заголовки, отметки времени.

### Кусок vs буфер записи vs воркер

- **Кусок** — единица Range-запроса и строка в индексе. Размер 1–4 MB (фиксирован при старте, подбирается под общий размер файла).
- **Read buffer** — сколько держим в RAM во время приёма тела Range-ответа. 64–256 KB. Это и есть ручка константной RAM: `buffer × число воркеров` — верхняя оценка пикового RAM на загрузку.
- **Воркер** — параллельная HTTP-Range-задача. Воркеры делят куски через общий atomic-счётчик «следующий `pending`» (work-stealing): свободный воркер берёт следующий кусок.

### Жизненный цикл куска

1. Воркер атомарно забирает следующий `pending` кусок `N`.
2. Открывает Range-запрос `[offset_N, offset_N + piece_size - 1]`.
3. Читает ответ потоком; каждые 64–256 KB тела — вызов `TPieceStorage::write_piece_bytes`. Тело куска целиком в RAM не попадает.
4. После последнего байта проверяет, что принято ровно `piece_size` (иначе кусок возвращается в `pending`).
5. Помечает кусок `done` в in-memory очереди батча.

### Батчевый коммит

Коммит на каждый кусок — дорого. `DownloadEngine` батчит: каждые **16 завершённых кусков** (или при `pause` / `shutdown` / перед `finalize`) вызывает `TPieceStorage::commit_batch`.

Инвариант, который обязана соблюдать любая реализация: **`done` ⇒ байты гарантированно сохранены**. Для `LocalPieceStorage` это `fsync(.data.brook)` + SQLite-транзакция (детали ниже). Для S3 — локальная запись ETag части.

`kill -9` между вызовами `commit_batch` — куски остаются `pending`, на рестарте перекачиваются. Потеря трафика — до 16 кусков × 1–4 MB ≈ 16–64 MB; корректность не страдает.

### Завершение (`LocalPieceStorage::finalize`)

Когда все куски `done`:
1. Финальный `fsync(.data.brook)`.
2. `rename` `<filename>.data.brook` → `<filename>`.
3. `<filename>.index.brook` удаляется.

### Ресюм и сбои (`LocalPieceStorage`)

Реализация `pending_pieces()`:

- **Чистый перезапуск процесса**: читаем `.index.brook`, докачиваем все `pending`-куски.
- **`.index.brook` повреждён или удалён**: доверять `.data.brook` нечем (часть `done`-кусков могла быть только в page cache и не долететь). Удаляем `.data.brook`, пересоздаём индекс, стартуем с нуля.
- **`.data.brook` удалён, индекс цел**: симметрично — удаляем индекс, стартуем с нуля.

## Сеть и устойчивость

### Range-загрузка и fallback

- На HEAD / `GET Range: bytes=0-0` подтверждаем: `Accept-Ranges: bytes` + валидный `Content-Range`. Без поддержки Range — fallback: один воркер, без кусков и пре-аллокации, дописываем в файл до EOF.
- На каждом куске ответ должен быть **`206 Partial Content`** с корректным `Content-Range: bytes X-Y/TOTAL`. `200 OK` на Range-запрос — сервер Range-неспособен → fallback.
- HEAD fallback: если HEAD вернул 4xx/5xx или не дал нужных заголовков — пробуем `GET` с `Range: bytes=0-0` (из `Content-Range` достаём размер, сам факт `206` — подтверждение Range).

### Защита от мутации файла на сервере

- На первом HEAD / Range-ответе ловим `ETag` (предпочтительно) или `Last-Modified`.
- В каждый последующий Range-запрос шлём `If-Match: <etag>` (или `If-Unmodified-Since`).
- Ответ `412 Precondition Failed` ⇒ источник изменился посреди загрузки. Загрузка помечается `FAILED` с понятной ошибкой (`source mutated`); пользователю — предложение рестартовать с нуля.

### Имя файла

Источник по приоритету: `Content-Disposition: attachment; filename*=` → `filename=` → последний path-сегмент URL → промпт пользователю в модалке `add`.

### Таймауты и ретраи

- **Connect timeout**: 10 s.
- **Read (idle) timeout**: 30 s без новых байт в теле Range-ответа → обрыв соединения + ретрай куска.
- **Retry**: экспоненциальный бэкофф `1s × 2^attempt` + jitter ±20 %, max delay 60 s, max 10 попыток на кусок.
- **Crash-loop guard**: 5 ретраев подряд с одной и той же ошибкой (DNS, 404, 401) ⇒ загрузка помечается `FAILED`, не крутим бесконечно.

### `pwrite` / `read`: короткие операции и `EINTR`

`pwrite(2)` и `read(2)` могут вернуться с частично обработанным буфером (сигнал, редкие ФС). Обёртка — loop до полного слива, пробрасывает только реальные ошибки (`ENOSPC`, `EIO`, и т. п.).

## Процессная безопасность

### Single-instance lock

Два `brookd` в одной CWD — гонка за `brook.db`, глобальную очередь, `.data.brook` в целевой папке. На старте `brookd` — `flock(LOCK_EX | LOCK_NB)` на `.brook.lock` в CWD. Вторая копия — exit с сообщением «brookd уже запущен в этой директории». TUI-клиент `brook` лок не берёт — сколько угодно клиентов могут одновременно подключаться к одному демону.

### Проверки перед стартом загрузки

- `statvfs` на целевую ФС: свободного места ≥ размер файла. Иначе — `FAILED` с понятной ошибкой, без попытки `F_PREALLOCATE`.
- Путь назначения — под `default_dir` из конфига либо явно заданный абсолютный путь; защита от path traversal.

### Graceful shutdown

`SIGTERM` / `SIGINT` в `brookd`:
1. Прекращаем приём новых команд через gRPC.
2. Пауза всех `DownloadEngine` — каждый доводит in-flight куски до batch-границы.
3. Финальный `fsync(.data.brook)` + batch-коммит `.index.brook` для каждой активной загрузки.
4. Закрываем gRPC-сервер, `./brook.db`, лог-writer, отпускаем `.brook.lock`.
5. Exit 0.

В TUI `brook` — `q` просто закрывает клиент, демон продолжает работать. Закрытие клиента при активных загрузках никак их не останавливает.

Без graceful shutdown на ctrl-c демона — теряем до 16 `done`-кусков трафика на каждую активную загрузку (перекачаются после рестарта).

## API-слой (`brook-api`)
- Генерируется из `.proto` через `tonic-build` в build.rs `brook-proto`.
- Тонкая обёртка вокруг `DownloadManager`: proto ↔ core.
- Запускается как фоновая задача бинаря `brookd`.
- Контракт — [api.md](api.md).

### Поток событий и Watch

- `DownloadEngine` внутри себя агрегирует счётчики в таймере 200 ms — эмитит один `Progress` за окно. State-changes проходят мимо таймера и уходят мгновенно.
- `DownloadManager` собирает события всех engines в центральный `broadcast::Sender<Event>` (ring 1024). Это единственная точка, откуда питаются Watch-клиенты.
- На каждого Watch-клиента `brook-api` спавнит fanout-задачу:
  1. При коннекте — эмитит `snapshot` по каждой известной загрузке (initial state).
  2. Читает центральный `broadcast`, конвертирует в proto `Event`, пишет в tonic tx.
  3. `tx.send().await` обеспечивает транспортный backpressure: при медленном клиенте fanout блокируется, broadcast-receiver отстаёт.
  4. При `RecvError::Lagged(n)` — запрашивает у `DownloadManager` свежие snapshot'ы всех активных загрузок и шлёт их клиенту, затем продолжает нормальный цикл.
- Гарантия для клиента: сколько бы `progress_tick`-ов он ни потерял, **state всегда догоняется** через `snapshot`.
- Протокольные детали (какое событие когда, что перезаписывает) — [api.md#watch-события-и-реконсиляция](api.md#watch-события-и-реконсиляция).

## UI-слой (`brook-tui`, бинарь `brook`)
- `ratatui` + `crossterm`.
- gRPC-клиент (`tonic::Channel`) к `brookd` на `127.0.0.1:<port>` (флаг `--port`, дефолт 7090).
- Две точки взаимодействия:
  - Команды — unary (`add`, `pause`, ...).
  - События — подписка на server-streaming (`Watch`); фоновая задача питает view-model.
- View-model мутируется **только** в ответ на событие от API.
- UX-детали — [ux.md](ux.md).

## Конфигурация

Вся конфигурация живёт в таблице `settings` внутри `./brook.db`. TOML-файлов нет. При первом старте `brookd` создаёт БД и сидит таблицу дефолтами. На каждом старте `brookd` читает значения и применяет их в `DownloadManager` и `brook-api`. Изменения на лету и API-методы на settings — см. [post-mvp.md](post-mvp.md). В MVP редактирование — напрямую через SQL (`sqlite3 brook.db`) при остановленном `brookd`.

Таблица `settings` — key/value: текстовый первичный ключ `key`, текстовое значение `value`.

Ключи и дефолты:

| key                          | default               | назначение                        |
|------------------------------|-----------------------|-----------------------------------|
| `download.default_workers`  | `4`                   | воркеров на файл по умолчанию     |
| `download.max_workers`      | `16`                  | потолок на файл                   |
| `download.max_concurrent`    | `3`                   | одновременно активных загрузок    |
| `download.default_dir`       | `~/Downloads`         | дефолтная папка назначения        |
| `download.on_duplicate_url`  | `ask`                 | `ask` / `skip` / `add`            |
| `download.on_file_exists`    | `ask`                 | `ask` / `rename` / `overwrite`    |
| `api.port`                   | `7090`                | порт gRPC                         |
| `api.bind`                   | `127.0.0.1`           | bind-адрес (только loopback в MVP)|
| `log.dir`                    | `~/Library/Logs/brook`| каталог JSON-логов                |
| `log.rotate_count`           | `10`                  | файлов в ротации                  |
| `log.rotate_size_mb`         | `50`                  | размер файла до ротации           |

Невалидное значение → ошибка старта `brookd` с явным сообщением и именем ключа. Неизвестные ключи в БД — warning в лог, игнорируются.

- `tracing` + JSON-форматтер во всех крейтах.
- `session_id` — xid, создаётся при старте процесса; прокидывается как поле во всех root-спанах.
- `download_id` — у каждой загрузки; `brook-core` входит в `span!(download_id = ...)` при любых операциях.
- gRPC-запросы получают `request_id`; если касаются конкретной загрузки — добавляется `download_id`.
- Лог-файлы: `~/Library/Logs/brook/brook-<session_id>.jsonl`. Ротация — [open question](open-questions.md).

## Тестирование
- `brook-core` — юнит + интеграционные без сети (`wiremock` или локальный тест-сервер). Отдельный тест: **пиковый RSS при длительной загрузке не растёт с размером файла** (проверка записи по кускам).
- `brook-api` — интеграционные: tonic-server + tonic-client в одном процессе, проверка контракта.
- `brook` — ручная прогонка квалификационных сценариев (см. [open-questions.md](open-questions.md)).
